Refactoring Cut Agent Costs 83% While GCC and OpenJDK Banned AI-Written Code

Refactoring Cut Agent Costs 83% While GCC and OpenJDK Banned AI-Written Code

July 31, 2026

Key Insights

The cheap-tokens story is over. Everyone has cheap tokens now. What landed this week is the bill that comes after cheap tokens — and it is being paid in review time, legal exposure, and code you cannot read.

Someone finally measured the cost of agent slop, and it is a line item. Giles Edwards-Alexander, CTO for EMEA and India at Thoughtworks, built a 150,000-line application — roughly 120 kLoC of Rust plus TypeScript and Terraform — entirely with Claude Code and Cursor. He did not read or review the code. Predictably, the data access layer metastasized into a single 17,155-line Rust file with no de-duplication, no extracted functions, and the same HTTP setup and JSON encoding copy-pasted into every query.

Then he ran the experiment that only agents make possible: because agents never learn between sessions, you can hand a fresh sub-agent the identical feature prompt after every refactoring step and get a clean measurement. Fifteen steps later, the cost of implementing the same change fell from 159,564 input tokens to 27,360 — an 83% reduction, with the drop concentrated in the final steps where the largest file shrank from 17,155 to 3,695 lines.

The mechanism matters more than the headline. Total lines of code in the data access layer barely moved — 17,155 down to 16,608, spread across 19 files. The savings came entirely from the agent being able to identify a smaller subset of files to read. Randomly chopping a big file into small files would not have worked; the agent would just read all of them hunting for the relevant code. The structure has to be legible, not merely divided.

And at exactly this moment, two of the most consequential compilers in software said no. The GCC steering committee accepted an AI contributions policy that declines any “legally significant contributions which include LLM-generated content or are derived from LLM-generated content,” using the GNU threshold of around 15 lines of code or text. OpenJDK’s Governing Board approved an interim policy going further: contributions “must not include content generated, in part or in full, by large language models, diffusion models, or similar deep-learning systems” — and it explicitly covers source code, text, images, pull requests, e-mail messages, wiki pages, and issue tracker entries. Both policies permit private use of LLMs to comprehend, debug, review, and research. Neither permits the output to ship.

The reason is reviewer economics, and OpenJDK says so plainly. Their stated risk is that generative tools “make it easy to create large quantities of plausible-looking code, with plausible-looking tests, which is nonetheless incorrect or, even if it is correct, is poorly designed and therefore difficult to maintain.”

Numbers that should change your decisions:

  • 159,564 → 27,360 input tokens for the same change. At Sonnet 5 pricing this particular saving is only about 40 cents, but it is 40 cents per change, forever, on one module of one app. Codebase structure is now a recurring cost curve, not an aesthetic preference.
  • ~15 lines. The GCC threshold above which an LLM-derived contribution gets declined. If your product touches open-source contribution workflows, provenance just became a hard requirement with a specific number attached.
  • 68%. Fifteen of 22 conference submissions reviewed by two researchers across NeurIPS, WACV, and a workshop at ECCV contained fabricated citations, fabricated author lists, or unmistakable LLM generation. Independent audits put roughly 146,900 hallucinated citations in 2025 papers, and found 85.3% of them survived from preprint into the published version. Detection is not happening downstream.
  • 21%. Share of ICLR 2026 reviews — 15,899 of them — that an AI-writing detector flagged as AI-generated. The slop flows in both directions, which means the verification layer itself is compromised.
  • A 13-year-old Chrome sandbox escape, found in early 2026 by a Gemini-driven agent harness, allowing a compromised renderer to trick the browser into reading local files. Google reports fixing more Chrome bugs in June than in the previous two years combined.

The synthesis: writing code stopped being the constraint; proving it is trustworthy became the constraint. That gap is where the buildable products are this quarter, and it is unusually friendly to a solo founder because it is a workflow problem, not a compute problem.

Market Trends

1. Codebase structure became a measurable, recurring cost

For thirty years the argument for refactoring was quality, maintainability, and developer happiness — real, but soft, and always the first thing cut under deadline. The Thoughtworks experiment converts it into arithmetic: every future change touching a module is priced by how much of that module the agent must read to make it.

This inverts an assumption that has quietly guided a lot of vibe-coded product work. If you never read the code, you assumed you had outsourced the maintenance problem. You did not. You converted it from a human legibility problem into a machine legibility problem, and the invoice arrives monthly in token spend and in the slow degradation of the agent’s ability to make correct changes.

Three details worth internalizing:

  • The savings arrive as a cliff, not a slope. Input tokens stayed essentially flat through the first six refactoring steps and only collapsed once the largest file dropped below roughly 4,000 lines. Partial refactoring looks like it is doing nothing right up until it works. If you measure after two steps and quit, you will conclude refactoring is worthless.
  • Output tokens barely moved — around 1,700 to 2,400 across every step. Since output tokens are typically five times the price of input, the ceiling on this particular optimization is real. The win is in reading, not writing.
  • The agent was bad at the refactoring itself. Claude could not look at code and independently determine which refactorings applied; it needed explicit human direction. The mechanical work was done with Python scripts using grep and sed, which “frequently got confused by indentation.” The full experiment took about eight hours, mostly unattended, with one human intervention at six hours forty minutes because a step had been silently skipped.

That last point is the honest state of agentic engineering in mid-2026: enormous throughput, near-zero judgment about its own output quality. Which is precisely why the next trend exists.

2. Provenance moved from ethics debate to compliance surface

GCC and OpenJDK landing within days of each other is not a coincidence, and it is not primarily about copyright ideology. Read the stated reasoning and it is operational: reviewer burden, safety, security, IP — in that order for OpenJDK.

What makes this commercially interesting is the shape of the rules. Both are narrow and specific in a way that creates tooling requirements:

  • They permit LLM use for comprehension, debugging, review, and research, and prohibit LLM content in the contribution. That is a distinction that has to be tracked, asserted, and audited — by a human today, by software tomorrow.
  • GCC attaches a numeric threshold (~15 lines) and carves out an exception: maintainers may accept LLM-generated test cases. Conditional policies need conditional enforcement.
  • OpenJDK’s scope covers e-mail messages and wiki pages, not just code. The compliance surface is the entire contribution footprint.
  • Both are explicitly provisional. GCC “expects the policy will evolve and will be revisited periodically.” OpenJDK’s is an interim measure while Oracle drafts a full policy for the Governing Board.

The HN response was predictably split, with the strongest objection being that the rules are unenforceable and that unenforceable rules “punish honesty” and breed contempt. That objection is correct about detection and wrong about consequence. Enterprises do not need perfect detection to require an attestation trail — they need a documented process, the same way SOC 2 does not prove your code is secure, it proves you have a procedure. When a large enterprise consuming GCC or the JDK asks its vendors whether their contributions comply, the answer will need to be a document, not a vibe.

3. The review layer is now the scarce resource — and it is itself contaminated

The peer review data is the clearest picture anyone has published of what happens when generation outruns verification. Two researchers, 22 submissions, 15 with fabricated citations, hallucinated authors, or nonsensical LLM writing. One of them hit 9 of 11. A Lancet audit across 2.5 million biomedical papers found the share containing at least one fabricated reference rose six-fold in two years — from one in 2,828 papers in 2023 to one in 458 in 2025, reaching one in 277 in early 2026. An analysis of 100 hallucinated citations in papers actually published at NeurIPS 2025 found every single one passed three to five expert reviewers.

Then the reversal: 21% of ICLR 2026 reviews were themselves flagged as AI-generated. The filter is made of the same material as the thing being filtered.

This exact dynamic is arriving in every domain where volume meets gatekeeping — app store submissions, grant applications, job applications, marketplace listings, PR queues, RFP responses. The pattern is identical: a review process calibrated for human production rates, hit by machine production rates, degrading into either rubber-stamping or paralysis.

Two responses are visible in the wild this week, and both are buildable by one person. The researchers who reported the 68% figure did not write a manifesto — they shipped an open-source bib-audit skill. And GitHub moved stacked pull requests into public preview (719 points on HN), which is fundamentally review-throughput infrastructure: when agents produce many small parallel changes, the bottleneck is the serialized review queue, and stacking is how you pipeline it. An indie developer shipped a local merge queue for parallel Claude Code agents on the same theme.

4. Agent interfaces are converging on the workspace, and away from the chat log

A Show HN this week — MarbleOS, “a workspace with visible files, tools, tasks, and outputs — not buried in chat threads” — drew 77 points and a substantive comment thread asking the right question: what should the GUI for AI agents look like?

The answer the market keeps converging on is: not a transcript. Once an agent takes 1,000+ actions across a filesystem, a chat log is the worst possible audit surface. You need to see what it touched, what it changed, what is pending, and what it spent. This is the same verification thesis wearing a UI hat.

Jim Nielsen’s widely-read piece on “the AI aesthetic” (345 points) documents the flip side: shimmering text, sparkle icons, tiny thin iconography, beige-and-orange serif landing pages, and non-deterministic UI that repaints under your cursor. An entire product category is starting to look identical. For anyone shipping a solo product, that homogenization is both a warning and an opening — visual and interaction differentiation is currently cheap, because almost nobody is attempting it.

Build Directions

Two questions, answered directly: what should you build, and what should you build it with.

The direction is verification and provenance infrastructure. The reason it fits a solo founder is that every product below is a workflow wrapped around cheap inference and public APIs, needs no proprietary data, has a buyer with a budget line, and is too small and unglamorous for a well-funded team to bother with.

Direction 1 — Contribution provenance and attestation for repos

What to build: A GitHub App that attaches a provenance record to every pull request: declared AI involvement, diff size against the policy threshold, contributor attestation, and an exportable audit log. Configure per-repo rules that mirror the actual published policies — GCC’s ~15-line legally-significant threshold with a test-case carve-out, OpenJDK’s blanket content prohibition, or a company’s own middle ground.

Stack: Octokit or Probot for the GitHub App; Cloudflare Workers or Fly.io for hosting; Postgres via Supabase or Neon for the audit log; a cheap model (DeepSeek V4-Flash at $0.14/$0.28 per million tokens, or GPT-5.6 Luna at $0.20/$1.20) for diff classification and summarization. Do not sell detection accuracy — sell the record. Detection is adversarial and you will lose that arms race.

Economics: Roughly 2–4 weeks to a usable v1. Inference cost per PR is fractions of a cent. Price at $19–49 per repo per month for companies, free for public OSS as distribution. Buyers: enterprises contributing to regulated or policy-bound OSS, and any team that has to answer a procurement questionnaire about AI in their supply chain.

Direction 2 — Agentic codebase health and token-cost linting

What to build: A CI check that answers one question no existing tool answers: what does this codebase cost your agents per change, and which files are responsible? Score modules by file size, duplication, and the read-footprint an agent needs to make a typical change. Output a dollar figure and a ranked refactoring queue. The Thoughtworks result gives you the validated headline — 83% reduction — and a reproducible methodology to benchmark against.

Stack: tree-sitter for language-agnostic parsing; tiktoken for token estimation; a GitHub Action for CI integration; optionally a sub-agent harness (Claude Code in headless mode) to run the “identical prompt after each step” measurement as a paid deep-scan tier. Start with one ecosystem you know well rather than claiming all languages.

Economics: 3–6 weeks to v1 if you scope to a single language. Near-zero marginal cost — most of the analysis is static. Price at $30–99 per month per repo, or sell the deep-scan as a one-off $500–2,000 audit, which is an easier first sale and funds the product.

Direction 3 — Reference and claim auditing as a workflow

What to build: The bib-audit skill is open source and free, which means the tool is not the product — the workflow is. Journals, conference program chairs, university research offices, and grant administrators need bulk submission processing, per-venue policy configuration, reviewer-facing reports, and a defensible paper trail. Same engine, packaged for an institution that cannot run a CLI.

Stack: Python with Crossref, OpenAlex, Semantic Scholar, and PubMed APIs for ground-truth verification; a cheap long-context model for citation extraction (DeepSeek V4-Flash’s 1M window handles a full paper in one pass); a plain web dashboard. The verification step is deterministic API lookup, not model judgment — which is exactly why this is defensible and why your false-positive rate will be defensible too.

Economics: 4–8 weeks. Institutional sales are slow but sticky and priced per venue or per seat — think $2,000–20,000 annually. The same engine generalizes directly to legal brief citation checking, where the buyer is more motivated and pays considerably more.

Direction 4 — Review throughput tooling for parallel agents

What to build: GitHub shipping stacked PRs validates the problem and does not finish it. The remaining gaps: orchestrating multiple agents against one repo without merge collisions, auto-splitting an oversized agent diff into a reviewable stack, and routing review attention to the parts of a diff most likely to be wrong. An indie developer already shipped a local merge queue for parallel Claude Code agents — proof of demand from someone with no funding.

Stack: Go or Rust CLI for the local daemon; GitHub API for stack management; git worktrees for agent isolation; a mid-tier model for risk-ranking hunks. Ship the CLI free and open source for distribution; charge for the team server that coordinates across developers.

Economics: 3–5 weeks for a credible CLI. Open-core, $10–25 per seat per month for the coordination layer. Distribution is unusually easy here — this audience reads HN and installs CLIs without a sales call.

Direction 5 — Vertical agent workspaces with a real audit surface

What to build: MarbleOS is going after the general case. The money in the near term is in verticals where “show me exactly what the agent did” is a regulatory or professional obligation rather than a preference — bookkeeping, legal document review, clinical coding, compliance filing. Same core idea, but the audit log is the feature, the file tree is scoped to a workflow, and every action is exportable as evidence.

Stack: Tauri or Electron for a desktop app that keeps client data local (a genuine selling point in these verticals); local inference via a small open-weights model for the routine passes with a frontier API call reserved for judgment; SQLite for a tamper-evident local action log.

Economics: 6–10 weeks — this is the heaviest option here. But professional buyers pay $50–200 per seat per month, churn slowly, and will tell you exactly what to build if you spend a week shadowing them first.

Choosing between them: if you want revenue fastest, Direction 2 sold as a one-off audit. If you want the largest eventual market, Direction 1. If you already have credibility in a profession, Direction 5. Do not attempt more than one.

Risk Factors

Detection is a losing product, attestation is a winning one. Every AI-detection business is in an arms race against models that improve monthly, and the HN objection is legitimate — these rules cannot be reliably enforced by inspection. Build the record, the workflow, and the audit trail. The moment your marketing page claims a detection accuracy percentage, you have set a trap for yourself.

The policies are explicitly interim and could reverse. GCC says it will revisit periodically; OpenJDK’s is a placeholder while Oracle drafts a real one. A softening in either direction — or an industry-wide standard that makes provenance a free platform feature — reprices your product overnight. Build for the general need (contribution audit trails) rather than for the specific policy text.

Google is giving away the adjacent thing. Chrome’s security team is shipping AI vulnerability discovery, triage, and patching as part of the browser, having found a 13-year-old sandbox escape with it. When platform owners absorb a capability into free infrastructure, thin wrappers around that capability die. Stay on the workflow, compliance, and organizational side, where platforms are structurally slow.

The capital environment is tightening under the AI trade. Citadel bought Situational Awareness’s stock portfolio after heavy AI losses, a widely-shared analysis argues the AI trade is running on borrowed money that lenders are now repricing, and the FT reported Korean retail investors nursing serious losses after the AI drawdown. Read this as: bridge rounds get harder, enterprise buyers scrutinize new line items more closely, and revenue in month three matters more than a narrative in month twelve.

Your product will look like everyone else’s. The AI aesthetic — sparkles, shimmer text, beige and orange, thin serif — has become a genre. If your landing page is generated by the same tools with the same defaults, you inherit the genre’s declining credibility along with its conventions. Differentiation is currently underpriced.

Action Recommendations

If you are early — pre-revenue, building solo:

  • ✅ Pick exactly one direction above and ship a v1 in under six weeks. Direction 2 sold as a fixed-price audit is the fastest path to a first invoice.
  • ✅ Before writing code, read the GCC policy and the OpenJDK interim policy in full. They are short, and they contain the precise language your customers will paste into a procurement form.
  • ✅ Instrument your own agent spend today. Log tokens per task by module. You need the baseline to sell the story, and you will discover your own 17,155-line file.
  • ✅ Distribute where this audience actually is: an open-source CLI, a GitHub Action, an HN Show post with real numbers in the title. The bib-audit release proves a free tool attached to a credible finding travels further than a launch page.
  • ✅ Sell the audit trail, never the detector.

If you are established — shipping product, paying customers:

  • ✅ Run the Thoughtworks experiment on your own largest module this week. Fresh sub-agent, identical prompt, measure input tokens, refactor, measure again. Eight hours mostly unattended. You will get a number you can put in a board update.
  • ✅ Do not stop refactoring after two steps. The savings arrived as a cliff at step 15, not a gradient. Budget the full pass or do not start.
  • ✅ Direct the refactoring yourself. The agent could not identify which refactorings applied and mangled indentation with sed. Plan with a chat interface, execute with the coding agent, review the plan personally.
  • ✅ Write down your own AI contribution policy before a customer asks. The threshold question (~15 lines?), the test-case carve-out, and the scope (code only, or e-mail and issues too?) all have precedent now.
  • ✅ Audit your review pipeline for the ICLR problem. If your team reviews agent output with agents, you have a filter made of the same material as what it filters.

What It Means

Every product decision this week points the same direction. Agents can write 150,000 lines of Rust that works. They cannot tell you whether it is any good, cannot refactor it without being told exactly how, cannot get a citation right, and cannot be trusted by a compiler project that has to live with the consequences for twenty years.

Generation is commoditized and still getting cheaper. Verification is scarce, getting scarcer, and is now backed by published policies with numeric thresholds, measurable cost curves, and institutions publicly admitting their review processes have failed.

The uncomfortable part for anyone who spent the last two years building generation wrappers: that market is finished. The comfortable part for anyone building alone: verification products are workflow products. They need no training run, no proprietary corpus, no GPU cluster — just a clear understanding of one buyer’s process and a few cents of inference per transaction. That is a solo founder’s shape of problem, and it is wide open right now.

Build the thing that proves the work is real.
